# AI6WIN 同引擎移植：高清文字、呈现与多核心优化笔记

记录日期：2026-09-23。实现基线：`9f238f3`；之前的显示正确性修复：`bdc9a53`。

这份笔记记录《鬼作》实际落地的方案，供同引擎另一游戏复用。**可以复用呈现结构、缓存与验证方法；游戏接口、图层编号、坐标、时序和字体作用域需要重新核对。** 本轮有主机回归、实际 SDL/GLES 像素检查和线程竞态检查，尚无 Switch 实机性能结论。原始素材与 PC 可执行文件不属于可复制的代码模块。

## 1. 保留原始逻辑分辨率，单独提高输出质量

原游戏仍按 640×480 处理 VM、图层、颜色键、Alpha、脚本截图、命中坐标、存档重建和动画。输出层将画面放到 1280×720 逻辑窗口中的 `(160,0,960,720)`，保持 4:3。

高清文字是在 FreeType 中按目标字号重新生成字形，例如 16×16 的逻辑字格对应 24×24 的输出字格；不是将原先16像素的字图拉大。背景仍是原始素材的重建放大，没有获得素材本来不存在的细节。

当前管线：

```text
主线程：输入 → VM/原生演出 → 原始640×480画面
                            │
                            ├─提交当前帧准备任务─────────┐
主线程：音频混音、SDL清屏    │                           │
                            │ 第三核：清除低清字的底图  │
                            │         +960×720文字层    │
主线程：等待当前任务完成 ←──┴───────────────────────────┘
        │
        ├─底图上传/复用 → GLES双线性采样及可选锐化
        ├─高清文字变化行上传/复用 → Alpha叠加
        └─模态面板、其他覆盖层、光标 → Present → 60Hz节拍
```

文字在底图锐化之后叠加，避免同一字形又被底图锐化加工。原版图片文字仍是图片；该方案不会自动将图集上的字变成高清矢量字。

## 3. 高清文字如何与原版图层同步

保留原始低清文字，另存高清伴随缓冲：

| 缓冲 | 《鬼作》尺寸 | 用途 |
|---|---:|---|
| `present_source_text` | 960×126 | 对应原始640×84文字源层 |
| `present_message_text` | 864×81 | 对应正文576×54的已揭示部分 |
| `present_choice_text` | 960×720 | 当前选项文字 |
| `present_shadow` | 640×84 | 核对原始文字源是否被其他指令改写 |
| `present_clean` | 640×480 | 供放大的无低清文字底图 |
| `present_reference` | 640×480 | 按原版方式含低清文字的比较参考 |
| `present_overlay` | 960×720 | 最终高清透明字层 |

这些表面按需分配，属于呈现状态，不写进原版图层或当成存档权威数据。640×480×4约1.17MiB，960×720×4约2.64MiB；迁移时要预算多份底图、文字层、上传快照和线程栈，不能只算一张输出纹理。

正文先写入高清源，再跟随原版逐字揭示复制相应矩形；一键全显、姓名前缀、清页、滑入滑出都必须同步。否则会出现“低清字还没出现，高清字已经全显”或旧字残留。

底图重建流程：

1. 按当前消息/选择框状态，绘制无文字底图。
2. 复制该底图，叠加原始低清文字，得到参考图。
3. 将参考图与真实原始画面比较。不同的像素可能来自日期、参数条、原生精灵等后绘制对象。
4. 将这些真实像素保留在底图中，并清除其覆盖范围内的高清字。比较时先检查整行；相同行不再逐像素循环。

遮挡像素映射当前使用 `x0=(x*3+1)/2`、`x1=((x+1)*3+1)/2`，Y同理；字形位置/尺寸则多用整数 `*3/2`。修改缩放比例时应重新定义取整规则，覆盖奇数坐标、边界和相邻矩形测试。

合成去重有具体前提：《鬼作》正文位于 y=404..457，按钮从 y=464 开始，二者应用相同滑动偏移，因此可以先画窗口/按钮，再叠加正文参考。另一游戏若按钮和文字相交，必须重新证明绘制顺序等价。

源层与 `present_shadow` 不一致，或处于信件、小说、部分消息淡化/转场时，当前代码保留原始画面。这是尚未接入的高清范围，**不能称这些模式已高清化**。上传失败则报错，不能把上传错误隐瞒成已正常显示。

## 4. 字体和描边的性能原则

本项目字体分工是用户指定的：外部OTF用于剧情正文/分支选择；历史、姓名输入等系统面板沿用HOS字体。另一游戏应单独确认，不能将所有 `draw_text` 统一换字体。

- CP932先解码成Unicode，再交给FreeType；不要把CP932字节当作Unicode码点。
- HOS/TTC字体显式选择合适的Unicode charmap。只成功打开字体不代表字符索引正确；过去出现过字格存在而字看不见的错误。
- 每个 `KFont` 独立缓存字形覆盖度和度量，键为码点、宽、高；当前上限1024字形、2MiB。位置和颜色不进入缓存键，换色不需要重新光栅化。
- 描边复用一次字形光栅化的结果：四方向1像素黑边用半Alpha，外侧2像素用四分之一Alpha，然后画正文。它不是FreeType轮廓描边器，像素半径以当前栅格为单位。
- 不能为描边在九个偏移位置各跑一次FreeType；曾由此造成明显卡顿。
- 字形缓存有可变LRU链表，`FT_Face`也有可变状态。同一字体实例不能被多个线程同时使用。

源码：[font.c](../runtime/font.c)、[高清合成入口](../runtime/bootstrap.c)。

## 5. 放大、锐化和颜色通道

当前正常路径使用自有GLES2纹理，源640×480，线性采样输出到960×720；强度读取 `[Display] CASStrength`，范围0..100，也接受带小数点的0..1值。未设置/0表示双线性放大而不锐化，**不等于nearest模式**。

现有着色器使用3×3邻域取min/max、四个正交邻居参与加权，权重含 `-0.2 × strength × amp`，最终限幅。项目历史记录称其CAS/RCAS；迁移时应称为“当前项目的限幅锐化实现”，不要仅凭名称或注释宣称与AMD官方实现逐式一致。

**已知实现边界：** GLES邻域偏移是一个源像素（`1/640,1/480`），CPU后备在放大结果的相邻输出像素位置取样；当前两者不是相同采样网格，也没有正式证明逐像素一致。当前GLES是一次pass中线性采样和锐化，并非先生成目标尺寸中间纹理、再运行第二次RCAS；没有实现Lanczos。若下个项目要求严格的两阶段算法或官方一致性，应独立实现和验证。

颜色约定必须写清楚：

- 游戏 `KImage` 是BGRA字节布局。
- SDL路径使用 `SDL_PIXELFORMAT_BGRA32`，由SDL负责底层解释。
- 自有GL纹理用 `GL_RGBA` 上传**未交换的BGRA字节**，着色器每次采样用 `.bgr`恢复RGB，最终整屏输出Alpha=1。
- 这一不透明输出只适用于最终底图，不能直接套给透明精灵。
- 不借用SDL纹理的native handle进行自定义采样。SDL可能在自己的shader中交换通道，绕过它会使肤色变蓝、黄围巾变青。

底图有变化才复制/上传；未变化只重绘自有纹理。padded stride只比较有效行，不将行尾填充当像素。测试入口保留 `--raw-present` / `--raw`；Switch上设置nearest曾出现黑屏，实际采样效果需要用棋盘格/读回检查，不应只看API返回成功。

## 6. 混用SDL和GLES时的状态边界

自定义pass前先 `SDL_RenderFlush`，避免尚在SDL队列中的命令被随后修改的GL状态影响。保存并恢复当前实际修改的所有状态：

- current program、active texture unit、unit0的2D纹理绑定；
- viewport、ARRAY_BUFFER绑定、UNPACK_ALIGNMENT；
- attribute 0/1的 enabled、size、type、normalized、stride、各自buffer绑定及pointer；
- blend和scissor的启用状态。

传客户端顶点指针之前必须绑定 `ARRAY_BUFFER=0`。若SDL留下VBO，未解绑时裸指针会被当成缓冲区偏移。恢复属性时先恢复该属性原来的VBO，再恢复pointer，最后恢复全局ARRAY_BUFFER。

**过去的关键回归：** 后处理改写并禁用了顶点属性，却继续让SDL使用其缓存的渲染状态，造成高清文字、鉴赏、历史、存档界面消失或串图。只在下一帧“重新画一次”不能修复SDL缓存失配。

当前pass没有修改的状态不必无目的地全查；将来若增加FBO、scissor矩形、blend函数、额外纹理单元或其他属性，必须扩展保存恢复及测试。不要为减少glGet开销直接删除必要的状态恢复。

## 7. 缓存与局部上传

`KTextureCache`持有独立像素快照及持久SDL纹理：

1. 首次创建或尺寸变化，分配纹理并上传全图。
2. 精确比较每行的有效字节，查找首个和最后一个变化行。
3. 仅上传两者之间的整行矩形；没有变化则不调用上传API。
4. 上传成功后更新快照；失败清理缓存，使下一次完整重建。

擦字和透明度变化也属于变化，不能只标记“新增字形”。局部上传数据指针从首个变化行开始，pitch仍是原图stride。两个距离较远的改动可能上传中间未变的行；这是当前简单实现的已知取舍，不是精细脏矩形系统。

当前用于高清文字和原生CG画面。底图GLES也有独立整帧比较缓存。存档/音乐等其他UI不应据此宣称都已使用同一局部上传缓存。

历史、原生CG已证明输出完整不透明面板，所以跳过其背后的剧情高清合成和锐化。其他半透明面板必须保留底图；不能仅凭“打开了菜单”就跳过背景。

历史字体缓存、CG纹理缓存分别验证“静止时不新增光栅化”和“不每帧创建/销毁纹理”。缓存命中不代表整帧零CPU开销，仍有像素比较、绘制和部分合成。

## 8. 多核心分工与线程所有权

| 工作 | 当前Switch分配 | 说明 |
|---|---|---|
| VM、输入、SDL/GLES、音频混音 | 主线程原有调度 | 此补丁没有显式把主线程绑定core 0 |
| 语音解码 | core 1，优先级0x2c | 独立归档、PCM结果交接 |
| 当前帧高清合成准备 | core 2，优先级0x2c | 1MiB栈；不碰SDL/GLES |
| 图片解码 | core 2，优先级0x2d | 让当前帧准备优先；同核竞争仍需实测 |

“第三核”指core 2，不是core 3。不要为了图表占用率而启动空转线程。worker通过条件变量等待，没任务就休眠；主机测试用pthread，不模拟Switch的实际核心分配。

`present_worker`不是整个bootstrap的通用并发锁。提交后，worker独占当前runtime的呈现、选项和字体状态；`bootstrap_present_layers`可能更新选项页和字形缓存，不能当成纯只读函数。

主线程在这一小段重叠区只执行已审查的音频混音和SDL清屏；当前混音仅更新音频游标并读取设置，不碰字体和选项。任何后续新增的并发工作都要重新审查。主线程必须等待后才能：

- 读取准备结果，绘制其他可能使用字体的UI；
- 推进VM、处理输入、切选项/菜单、修改设置；
- 替换存读档runtime、释放字体/图层、退出程序。

任务仅准备当前帧，不能在未消费结果时再次提交；没有多帧队列，不故意增加一帧延迟。输出是runtime内部表面的借用指针，下一轮修改/销毁runtime前就必须用完。异常退出也先 `present_worker_clear` 等待任务、join线程，再释放runtime和SDL资源。

## 9. 帧率与性能证据

主循环请求VSync，并按 `SDL_GetPerformanceFrequency()/60` 的累计期限调度，余数累计避免长期截断漂移。目标上限60 FPS；负载过重时会低于60。20ms/15ms原生演出时钟仍由原有逻辑处理，不能为降负载随意减掉VM帧或改变原版动画结束条件。

固定主机检查点的结果：

| 检查 | 结果 | 不能推出什么 |
|---|---|---|
| 300次稳定HQ准备，对比bdc9a53 | 108.672ms → 62.990ms，约减少42% | 不是总CPU下降42%，也不是Switch实测 |
| raw/clean/overlay与附加遮挡后的哈希 | 前后完全一致 | 不覆盖全路线所有图层组合 |
| 100帧稳定底图 | 1次GL上传 | 不代表100帧只执行一次pass |
| 30帧稳定960×720文字 | 1次SDL上传 | 不代表所有合成都缓存住了 |
| CG面板12帧 | 1次纹理上传 | 变体切换/动画帧仍需更新 |
| 单行变化、擦除、底行变化 | 局部上传与全图上传的GPU画面一致 | 不验证所有驱动的性能 |
| 串行/worker、真实开场与选项、混音重叠、销毁等待 | 像素一致，TSan未报告竞态 | 不代替Switch长时间运行 |

后续实机测量应分开记录：VM/原生合成、准备任务总耗时、主线程等待时间、上传、GL绘制、VSync等待；同时记录画面/设置/频率模式。第三核负载升高只表示工作转移，不能单独证明帧时间改善。

## 10. 建议迁移顺序

1. 先确定另一游戏原始分辨率、像素格式、Alpha语义、编码、原生文本矩形和图层所有权；保留可运行的原始呈现基线。
2. 单独接放大pass，先用纯色、棋盘格、不同stride和半透明边缘检查颜色、方向、采样与裁剪；先不接线程。
3. 用实际SDL renderer，在pass后连续绘制文字、CG/音乐/视频/回想、历史、存读档，确认没有SDL状态污染。
4. 接高清伴随文字，从普通正文和选择框开始；覆盖逐字、瞬显、清页、姓名前缀、菜单覆盖和原生精灵遮挡。信件/小说单独实现。
5. 接字形缓存、纹理复用及变化行上传；比较局部上传与全图上传，包括透明擦除和换runtime。
6. 先在单线程下减少重复合成，拿固定状态与优化前逐像素对比。
7. 再接worker，明确独占区和可重叠工作。跑串行/并行对比、TSan、提交后退出/读档切换检查。
8. 最后交叉编译、打包、实机测帧时间与稳定性。若GPU路径未启用、进入CPU后备，应先查清原因再讨论多核收益。

每一步留下独立commit及可复现结果。`bdc9a53`适合追溯正确性修复，`9f238f3`适合查看优化差异；二者包含《鬼作》专用代码，不能无审查地整体cherry-pick到另一游戏。

## 11. 当前项目的复验命令

在仓库根目录运行，原始 `鬼作/` 保持只读：

```sh
./build-host.sh
./test-host.sh 鬼作

tools/test_present_gles.sh local/fonts/arshanghaisonggbpro_lt.otf 鬼作

mkdir -p local/hires-note-check local/present-note-bench
build/kisaku-bootstrap-test 鬼作 local/hires-note-check --hires
build/present-benchmark 鬼作 local/present-note-bench

./build-switch.sh
python3 tools/package_sd.py 鬼作
shasum -a256 build-switch/kisaku.nro 交付/SD卡根目录/switch/kisaku/kisaku.nro
```

`tools/test_present_gles.sh`默认依赖macOS Homebrew Mesa路径，可用 `KISAKU_MESA_PREFIX`更改；脚本当前库名为`.dylib`，移到其他主机要适配。实际renderer是Mesa offscreen/llvmpipe，不是Switch GPU。测试的“逐像素一致”主要针对状态恢复、叠加和上传；不代表CPU/GPU非零锐化强度或AMD官方算法一致。

线程检查：按 `build-host.sh` 中 `tests/kisaku_bootstrap_test.c` 的同套源文件和链接库构建，改用 `-O1 -g -fsanitize=thread`，输出例如 `build/present-worker-tsan`，再运行：

```sh
mkdir -p local/present-thread-check
TSAN_OPTIONS=halt_on_error=1 build/present-worker-tsan 鬼作 local/present-thread-check --hires
```

不要只检查编译成功或软件renderer截图。至少检查一次**实际SDL/GLES管线中的菜单+高清文字**，再单独保留Switch实机“已验证/未验证”记录。

## 12. 仍待补齐或不能直接推广的部分
